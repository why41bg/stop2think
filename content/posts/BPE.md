# 第一部分：三种常见 tokenization 粒度

语言模型无法直接“读懂”文本，它只能处理被切成离散 token 的数字序列。切分方式决定了词表大小、泛化能力和部署成本。下面用尽量直白的语言把三种主流粒度讲清楚。

## word-based tokenization

word-based 把空格或标点当作边界，像 “I love coding” 会变成 `["I","love","coding"]`。优点是含义和人类语言对齐；缺点是词表动辄几十万，每出现一个没见过的新词（OOV）就只能用 `[UNK]` 代替，对词形变化丰富的语言非常痛苦。

## character-based tokenization

character-based 切到最细，一次只看一个字符（甚至一个字节），词表只有 128～256 个 token，永远不会 OOV。但序列会变得很长，模型必须学会把几十甚至上百个字符“拼”成单词，训练和推理都更慢。

## subword-based tokenization

subword 介于两者之间：常见词保留为一个 token，罕见词拆成更小的片段（如 `un + ##common`）。这样既能覆盖所有文本，又能保持序列长度适中，是现代 LLM 的主流选择。

# 第二部分：Subword 算法概览与 BPE 流程

## 常见 subword 算法

- **BPE (Byte Pair Encoding)**：逐步合并出现频率最高的符号对，最经典也最易实现，GPT-1/2 及不少翻译模型使用。
- **WordPiece**：Google 提出的变体，用最大化语料似然的方式决定合并，BERT/ALBERT 等采用。
- **Unigram Language Model**：直接假设一套候选 subword 的概率分布，用 EM 反复迭代，SentencePiece 默认算法。
- **SentencePiece**：工具链，兼容 BPE/Unigram，并支持以原始字节为单位，方便多语言或含 emoji、代码的语料。

它们的共同目标都是：用有限的词表覆盖尽量多的文本，同时避免序列过长。

## BPE 的逐步流程

1. **准备语料与初始词表**  
   读入训练语料，通常在单词末尾加 `</w>` 之类的分隔符，保证合并不会跨单词；初始词表就是所有基础符号（字符或字节）。
2. **统计相邻符号对频率**  
   把每个单词拆成符号序列，统计所有相邻符号对的出现次数，例如 `lower` 会贡献 `l o`、`o w`、`w e` 等。
3. **合并最高频符号对**  
   选出频率最高的符号对，把它们视为新符号加入词表，并在语料里替换；重复统计→合并，直到词表达到目标大小（如 50k）。
4. **形成编码/解码规则**  
   合并顺序就是编码时的匹配规则：给定新词，按照训练得到的“合并表”从左到右匹配最大的子串；解码时再按相反顺序拆开并去掉分隔符。

### 迷你示例

语料为 `["low", "lower", "newest", "widest"]`：

1. 初始化词表为字符加 `</w>`，每个词拆成字符序列。  
2. 假设 `e s` 频率最高，合并为 `es`；下一轮也许是 `es t` → `est`，于是 `newest` 被编码为 `new est </w>`。  
3. 继续迭代后，`low` 可能变成单个 subword，而 `widest` 被表示为 `wi d est </w>`。  

因此即使遇到新词 `lowest` 也能编码为 `low est </w>`，不必退回字符级。

### 实践要点

- **语料覆盖面越广越好**，能减少推理时退回字符的情况。  
- **词表大小要权衡显存与序列长度**；更大的词表减少 token 数，但 embedding 矩阵更大。  
- **空格与大小写处理**：GPT 使用 `Ġ` 表示“词首空格”，方便区分 `token` 和 `##token`。  
- **直接在字节层工作** 可以天然支持 emoji、代码和多语言输入，不必额外清洗。

### 优势与局限

- 优势：实现简单、词表可控、编码快、对 OOV 友好。  
- 局限：完全依赖频率，无法利用语义；极稀有片段仍需退回字符；压缩与信息保留之间没有全局最优保证。

理解 BPE 之后，再读 WordPiece、Unigram 或 tiktoken 的实现就容易多了——它们只是用不同策略决定“该合并谁”，目标始终是构建一个稳定、泛化性好的 subword 词表。
